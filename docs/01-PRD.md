## 1. 왜 만드는가 (스코프 판단의 기준선)

1차 목적은 **작동하는 서비스를 빠르게 내놓는 것**, 2차 목적은 **그 과정을 TIL로 남겨 백엔드 역량을 증명하는 것**.

기능 추가로 고민될 때의 판정 기준:

## 3. 게임 구조

게임은 **두 개의 독립된 축**으로 이루어진다. 이 둘을 섞지 않는 것이 확장성의 전부다.

```
[축 1] 게임 모드 — 곡을 어떻게 고르고 누구와 하는가
├── 싱글 · 데일리      하루 1회, 전 유저 동일 문제
├── 싱글 · 올랜덤      전체 곡 풀에서 무작위
├── 싱글 · 범위지정    프로듀서/보컬/연도/가사언어/인기도 필터
└── 멀티 · 스피드퀴즈  걸린 시간 대비 차등 점수          (Phase 4)

[축 2] 퀴즈 유형 — 한 문제를 어떻게 내고 어떻게 채점하는가
├── AUDIO_SEGMENT   구간을 통째로 듣고 맞히기          (Phase 1)
├── INTRO_GUESS     0초부터 0.5초→16초로 늘려가며 맞히기
├── SCENE_*         장면 보고 맞히기 (용도별)
├── VIEW_BATTLE     A vs B 조회수 대결
└── ...             계속 추가된다                      ← 여기가 확장점
```

**두 축은 서로를 모른다.** 데일리로 장면 퀴즈를 돌리든 범위지정으로 인트로 퀴즈를 돌리든
조합은 자동으로 성립해야 한다 (D-005).

### 3.1 퀴즈 유형은 늘어난다 — 설계의 1급 요구사항 (D-005)

> **새 유형 추가 비용의 목표:** 백엔드 클래스 1개 + 프론트 컴포넌트 1개.
> **DB 마이그레이션 0, 기존 코드 수정 0.**

서버·프론트 어디에도 `if (type == AUDIO_SEGMENT)` 분기를 두지 않는다.
계약은 `docs/02-ARCHITECTURE.md` §4.

### 3.2 퀴즈 유형 카탈로그

| 코드             | 출제 내용                                                 | 답안            | 채점        | 상태        |
| ---------------- | --------------------------------------------------------- | --------------- | ----------- | ----------- |
| `AUDIO_SEGMENT`  | 구간(5~20초) 통째 재생                                    | 곡 선택         | 유형이 정함 | **Phase 1** |
| `INTRO_GUESS`    | 0초부터 0.5/1/2/4/8/16초 (D-046)                          | 곡 선택         | 단계별 감점 | Phase 3     |
| `SCENE_*`        | 지정 시점의 정지 화면 (모자이크 / 여러 장 / 직접 찍은 곳) | 곡 선택         | 유형이 정함 | Phase 3     |
| `VIEW_BATTLE`    | 곡 2개의 조회수 대결                                      | A/B             | 1회 제출    | Phase 5     |
| `LYRIC_BLANK`    | 가사 빈칸                                                 | **자유 텍스트** | —           | 후보        |
| `PRODUCER_GUESS` | 구간 듣고 프로듀서 맞히기                                 | 프로듀서 선택   | —           | 후보        |
| `RELEASE_ORDER`  | 곡 3개 발매순 정렬                                        | 순서 배열       | 부분 점수   | 후보        |

후보 유형은 **만들 계획이 아니라 계약이 견디는지 검증하는 테스트 케이스**다 (설계 문서 §4.3).

**중요 (D-018):** "점점 길게 들려주기"는 `INTRO_GUESS` **한 유형에만** 적용한다.
일반 오디오 퀴즈는 구간을 통째로 한 번 들려준다.

**중요 (D-026):** 장면 퀴즈는 세 갈래로 미리 쪼개지 않는다. 검수자가 장면마다
**시점 + 용도**를 적고, 퀴즈 유형이 필요한 용도의 장면을 가져다 쓴다.

### 3.3 채점 방식은 유형이 소유한다 (D-023)

단일 점수 공식은 없다.

| 방식            | 설명                                   |
| --------------- | -------------------------------------- |
| `SINGLE_SHOT`   | 1회 제출. 맞으면 만점, 틀리면 0        |
| `TIME_BASED`    | 걸린 시간으로 차등. **서버 시계 기준** |
| `ATTEMPT_BASED` | 시도 횟수로 감점                       |
| `HINT_BASED`    | 쓴 힌트 수로 감점                      |

> **단 하나의 전역 규칙: 라운드 점수는 반드시 `0..100`.**
> 이 정규화가 있어서 서로 다른 채점 방식의 유형을 한 게임에 섞어도 총점이 성립한다.

- 한 게임 = 10라운드 (데일리 5라운드). 총점 = 라운드 점수 합.
- 멀티 스피드퀴즈: `round(100 × (1 − 0.7 × min(elapsed/limit, 1)))` → 즉답 100, 만료 직전 30.

### 3.4 힌트 (D-029)

**이미 DB에 있는 것만 공개한다.** 프로듀서, 발매 연도, 제목 글자 수, 첫 글자 등.
가사는 쓰지 않는다 — 수집 비용도 크고 저작권 리스크가 D-001을 세운 이유와 같은 종류다.
힌트 콘텐츠를 따로 제작하지 않으므로 입력 비용이 0이다.

### 3.5 출제 단위는 사람이 찍은 "구간" (D-017, D-020)

```
Song 선택   ← 게임 내 중복 방지는 여기서
  └ Video 선택
      └ Segment 선택
```

- 검수자가 한 영상에 **여러 개의 구간**을 찍는다. 길이 5~15초, 최대 20초.
- **구간이 없는 곡은 출제되지 않는다.** 곡이 DB에 있어도 나오지 않는다.
- 구간을 여러 개 찍으므로 같은 곡을 다시 만나도 다른 문제가 된다.
- 구간마다 곡 구조 태그를 붙인다: `INTRO / VERSE / PRE_CHORUS / CHORUS / INTERLUDE / OUTRO` (D-024).
  "후렴만 출제", "골고루 출제" 같은 방식이 여기서 나온다.
- **정답은 언제나 원곡(Song) 제목이다.** 셀프커버 영상이 재생되어도 마찬가지다 (D-006).

### 3.6 데일리 규칙

- 날짜(KST)를 시드로 곡을 뽑는다 → 전 유저가 같은 문제를 푼다.
- **하루 1회.** `(user_id, play_date)` 유니크 제약으로 강제.
- 워들 스타일 결과 공유 텍스트를 만들어 준다.
- **로그인 필수.** 익명이면 캐시를 지우고 무한 재도전이 된다.

### 3.7 범위지정 필터 축

| 필터           | 근거 데이터              | 결정      |
| -------------- | ------------------------ | --------- |
| 프로듀서       | `song_credit` (다대다)   | D-053     |
| 보컬           | `song_vocal` (파생 캐시) | D-050     |
| 발매 연도      | `video.published_at`     | —         |
| **곡의 언어**  | `song_language` (다대다) | **D-051** |
| 인기도         | `video.view_count`       | D-034     |
| 구간 구조 태그 | `segment.structure_tag`  | D-024     |

**언어 필터는 의도된 교환이다 (D-051):** 이 필터를 걸면 유명한 곡 일부가 잘려나간다.
그 대신 난이도와 일관성을 얻는다. 일본어와 한국어로 함께 불리는 곡은 두 필터 모두에 걸린다.

- 필터 결과가 필요한 곡 수보다 적으면 **게임 시작 거부.** 프론트에 "N곡 선택됨"을 항상 표시.

## 4. MVP 범위 (Phase 1)

**포함:**

- **관리자 페이지** — 곡 등록·목록, **구간 찍기** (D-030)
- **Google OAuth2 + 관리자 화이트리스트** (D-032)
- 싱글 · 올랜덤 · `AUDIO_SEGMENT` 한 유형
- `QuizType` 확장 계약 (구현체는 하나지만 계약은 유형 N개를 전제로) — D-005
- 곡 데이터: 유명곡 목록은 수동 선별, 메타데이터는 `videos.list`로 자동 (D-039)
- 게임은 익명 플레이 (세션 기반)
- 자동완성 입력으로 정답 선택

**명시적으로 안 하는 것:**

- ❌ 랭킹 / 리더보드
- ❌ 데일리 (Phase 2)
- ❌ 멀티플레이 (Phase 4)
- ❌ `AUDIO_SEGMENT` 외의 퀴즈 유형 (계약만 만들고 구현체는 하나)
- ❌ 범위지정 필터 (Phase 3)
- ❌ 채널 감시 자동 파이프라인 (Phase 3)
- ❌ 다국어 UI (데이터 구조는 준비하되 화면은 한국어만)
- ❌ 프로필, 아바타, 친구, 댓글, 좋아요

> **관리자 페이지가 MVP에 들어온 것은 원래 계획이 뒤집힌 결과다 (D-030).**
> D-017로 "구간이 없으면 출제 불가"가 되면서, 관리자 페이지는 편의 기능이 아니라
> **게임의 전제 조건**이 되었다.

## 5. 개발 순서

### Phase 1 내부 순서는 강제된다 (D-033)

구간이 없으면 게임을 만들 수 없으므로:

```
1. 스캐폴딩 + OAuth2 + 관리자 화이트리스트
2. 곡 / 영상 / 구간 도메인 + videos.list 연동
3. 관리자 — 곡 등록 · 목록
4. 관리자 — 구간 찍기 화면        ← 가장 어려운 화면
5. 구간 데이터 채우기              ← 30~50곡이면 충분. 300곡을 다 채우지 않는다
6. 게임 도메인 + QuizType 계약
7. 게임 API
8. 게임 프론트
```

**알고 가는 대가:** 가장 어려운 화면이 맨 앞에 오고, 게임이 도는 걸 보기까지 오래 걸린다.
1인 개발에서 동기가 꺾이기 가장 쉬운 구간이다. **5번에서 30곡만 채우고 6번으로 넘어간다.**

### 전체 Phase

| Phase | 내용                                             | 완료 판정                                                 |
| ----- | ------------------------------------------------ | --------------------------------------------------------- |
| **1** | 관리자 + 인증 + 구간 + 싱글 `AUDIO_SEGMENT`      | 브라우저에서 10라운드 완주하고 점수를 본다                |
| **2** | 배포 + 데일리 + Flyway                           | 남에게 URL을 보낼 수 있다                                 |
| **3** | `INTRO_GUESS` · `SCENE_*` + 범위지정 + 채널 감시 | **유형 추가 diff에 `quiz/types/`·`quiz/` 밖 파일이 없다** |
| **4** | 멀티플레이 (WebSocket/STOMP)                     | 브라우저 2개로 한 판을 끝낸다                             |
| **5** | `VIEW_BATTLE`                                    | 곡 2개·1회 시도 유형이 마이그레이션 없이 들어간다         |

**Phase 3과 5의 완료 조건이 "기능 동작"이 아니라 "diff가 작다"인 것에 주목할 것.**
검증할 가설은 "이미지 모드를 만들 수 있다"가 아니라 **"유형을 늘려도 비용이 안 는다"**이다.

## 6. 곡 수급

### 6.1 초기 데이터 (D-039)

- **"어떤 곡을 넣을지"는 사람이 고른다.** videoId 목록을 직접 만든다.
- **제목·설명문·길이·조회수·게시일·채널은 `videos.list`가 자동으로 채운다** (id 50개당 1 unit).
- 채널 전량을 통째로 넣지 않는다. 어차피 병목은 구간 찍기다.

### 6.2 운영 중 유입 (D-008, D-011, D-022)

```
프로듀서 채널 RSS 폴링 (쿼터 0)
  └ 새 videoId 감지
      └ videos.list로 상세 확보 (1 unit)
          └ AI 판별: 노래인가? + 기존 곡의 다른 버전인가?
              └ 사람이 결정 ── 새 곡 / 기존 곡에 병합 / 폐기
                  └ 사람이 구간을 찍어야 비로소 출제됨
```

- **AI는 후보만 제시하고 판단하지 않는다** (D-011). 보카로는 제목이 비슷한 별개 곡이 흔해서
  자동 병합은 오판 시 정답 판정을 깨뜨린다.
- **파이프라인은 "찾기"만 한다** (D-022). 곡 수가 늘어도 즉시 콘텐츠가 늘지는 않는다.
  검수 대기열이 쌓이는 것은 정상이며, 카탈로그 품질을 보장하는 대가다.

### 6.3 vocaloard (D-035, D-047)

`https://vocaloard.injpok.tokyo` — YouTube 기반 보카로 일일 랭킹.

- 제공: 곡 제목, 프로듀서, **보컬**, 게시일, videoId, 순위
- **보컬 정보가 여기서만 온다.** YouTube Data API는 보컬을 알려주지 않는다.
- JSON API 없음 → HTML 스크래핑. **1일 1~3회만 접속** (D-047).

## 7. 리스크

### 7.1 🔴 치팅은 원천 차단이 불가능하다

IFrame Player로 재생하는 이상 클라이언트가 `videoId`를 안다. 개발자 도구를 열면 답이 나온다.

**막을 수 있는 것만 막는다:**

- ✅ 정답은 라운드 종료 전까지 서버에서 절대 내려보내지 않는다
- ✅ 채점은 100% 서버. 클라이언트의 "맞았어요"는 무시
- ✅ 시도 횟수·진행 상태·경과 시간은 전부 서버 기록값
- ⚠️ `videoId` 노출은 **수용한다.** 막으려면 오디오를 직접 서빙해야 하고 그건 저작권 리스크를 서버가 떠안는 일이다
- 📌 랭킹은 공식 기록이 아니라 재미 요소로 포지셔닝한다

### 7.2 🟡 YouTube 이용약관

- 오디오 추출·영상 재서빙은 **ToS 위반.** 하지 않는다 (D-001).
- ToS는 플레이어를 가리거나 숨기는 것도 제한한다. 오디오 모드는 본질적으로 저촉 소지가 있다.
  - **완화:** `display:none`으로 죽이지 않고, 정답 공개 후 정상 크기 플레이어로 곡을 보여준다.
  - 이건 "안전하다"가 아니라 **"리스크를 알고 선택했다"**는 기록이다.

### 7.3 🟡 API 쿼터 (D-034, D-043)

- 하루 **10,000 units.** `videos.list`·`playlistItems.list`·`channels.list`는 각 1 unit.
- **`search.list`는 호출당 100 units — 하루 100번이 끝이다. 코드 어디에도 쓰지 않는다.**
- `videos.list`가 `search.list`를 대체하는 게 아니다. 하는 일이 다르다.
  **검색이 필요해지는 순간이 설계가 틀어진 신호다** (D-043).

### 7.4 🟡 자동화할 수 없는 것 (D-015, D-016)

| 원하는 것                | 왜 안 되나                                              |
| ------------------------ | ------------------------------------------------------- |
| "가장 많이 다시 본 부분" | 공식 API 없음. 스크래핑뿐이고 신곡엔 데이터가 없다      |
| 무음 구간 자동 감지      | 서버가 오디오를 갖지 않고, IFrame 오디오는 cross-origin |
| 임의 시점 프레임 추출    | 영상 다운로드 필요 → D-001 위반                         |

→ **구간 찍기는 사람이 한다.** 이것이 D-017의 근거다.

### 7.5 🟡 프론트엔드

React 선택의 비용(CORS·빌드·배포 3~4시간)에 더해, **D-030으로 첫 번째 화면이
구간 찍기가 되었다.** 플레이어 임베드 + `getCurrentTime()` 폴링 + 시작/끝 마킹 +
미리듣기 + 태그 선택. 프론트가 익숙하지 않은 상태에서 가장 어려운 화면부터 시작한다.

**비용 절감 규칙:** 상태 관리 라이브러리 금지, UI 킷 하나로만 조립, CSS 직접 작성 금지, TypeScript 사용.

## 9. 용어 정의 (코드/문서에서 이 단어만 쓴다)

| 용어           | 의미                                          | 쓰지 말 것              |
| -------------- | --------------------------------------------- | ----------------------- |
| **Song**       | 곡 하나. 출제·정답의 단위                     | Music, Track            |
| **Video**      | 곡에 딸린 영상 (본가/커버/MV/라이브)          | Clip                    |
| **Segment**    | 사람이 찍은 재생 구간 또는 장면 시점          | Clip, Section, Range    |
| **Game**       | 한 판                                         | Session, Match          |
| **Round**      | 한 문제                                       | Question, Quiz, Problem |
| **Attempt**    | 한 라운드 안의 시도 1회                       | Try, Guess              |
| **QuizType**   | 축 2 — 문제 유형                              | Mode, Category          |
| **GameMode**   | 축 1 — DAILY/RANDOM/CUSTOM/MULTI              | Type, Kind              |
| **payload**    | 라운드의 출제 데이터 + 정답 (서버 전용)       | data, content           |
| **view**       | 클라이언트에 내려보내는 출제 정보 (정답 제외) | dto, model              |
| **answer**     | 클라이언트가 제출하는 답안 봉투               | input, submit           |
| **IngestItem** | 채널 감시가 발견한 검수 대기 항목             | Candidate, Queue        |

용어를 흔들지 않는 것이 1인 개발에서 가장 값싼 생산성 향상이다.
