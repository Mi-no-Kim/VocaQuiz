# 결정 로그

**이 파일이 진실의 원천이다.** 다른 문서(`01-PRD`, `02-ARCHITECTURE`, `03-PROMPTS`)는 여기서 파생된다.
충돌하면 이 파일이 이긴다.

규칙:

- 확정된 것만 `[확정]`으로 적는다. 결정하지 않은 것은 `[보류]`로 남기고, 무엇을 알아야 정할 수 있는지 적는다.
- 번호는 재사용하지 않는다. 뒤집힌 결정은 지우지 말고 `[폐기]`로 표시하고 왜 뒤집혔는지 적는다.
- 결정을 코드보다 먼저 적는다.

### D-002 · YouTube Data API 쿼터를 소비하는 동작은 하지 않는다 `[개정됨 → D-034]` 2026-09-04

> ⚠️ **뒤집혔다.** 아래 '쿼터 없이 쓸 수 있는 수단' 표는 여전히 유효하지만,
> "Data API를 쓰지 않는다"는 전제는 D-034로 폐기되었다.

쓸 수 있는 것 (전부 API 키 불필요, 쿼터 없음):

| 수단                                         | 얻는 것                                         | 비고                         |
| -------------------------------------------- | ----------------------------------------------- | ---------------------------- |
| IFrame Player API                            | 재생 제어                                       | 게임의 핵심                  |
| `youtube.com/oembed?url=...`                 | 제목, 채널명, 썸네일 URL                        | JSON, 키 불필요              |
| `youtube.com/feeds/videos.xml?channel_id=…`  | **채널 최근 15개 영상** (videoId, 제목, 게시일) | XML RSS                      |
| `youtube.com/feeds/videos.xml?playlist_id=…` | 재생목록 최근 15개                              | XML RSS                      |
| `img.youtube.com/vi/{id}/maxresdefault.jpg`  | 썸네일 이미지                                   | 직접 접근                    |
| WebSub (PubSubHubbub)                        | 채널 새 영상 **푸시 알림**                      | 공개 URL 필요 → Phase 2 이후 |

얻을 수 없는 것: **조회수, 좋아요 수, 영상 길이, 정확한 설명문.**
→ 이 중 조회수 부재가 A vs B 대결에 직접 영향 (D-009).
→ 영상 길이는 IFrame Player가 재생 시작 후 `getDuration()`으로 알려주므로 클라이언트에서 확보 가능.

### D-006 · 출제 단위는 노래, 영상은 그 아래 `[확정]` 2026-09-04

```
Song  1 ─── N  Video
```

- **출제 흐름: 먼저 `Song`을 고르고, 그 곡에 딸린 `Video` 중 하나를 랜덤으로 고른다.**
- **정답은 언제나 원곡(`Song`) 제목이다.** 셀프커버 영상이 재생되어도 정답은 원곡 제목.
- 한 게임 안의 중복 방지는 `Song` 단위로 하면 자동 해결된다 (같은 곡이 다른 영상으로 두 번 나오지 않음).
- 프로듀서(작곡가)는 `Video`가 아니라 `Song`에 붙는다.

### D-007 · 언어는 ko / en 두 가지 `[개정됨 → D-036]` 2026-09-04

> ⚠️ 표시·검색 규칙은 유효. **저장 구조가 컬럼에서 테이블로 바뀌었다** (D-036).

- **표시: 현재 언어 제목 + 원제 병기.** 예) `센보자쿠라 (千本桜)`, `Senbonzakura (千本桜)`
- **검색(자동완성): 언어 설정과 무관하게 전 언어 매칭.**
  한국어 UI에서 `senbonzakura`, `千本桜`, `천본앵` 무엇을 쳐도 후보에 뜬다.
- 데이터 요구: 곡마다 `title_ko` / `title_en` / `title_original` 필수, 별칭 N개 선택.

### D-008 · 곡 수급은 "프로듀서 채널 감시" 파이프라인 `[방향 확정 · 상세 보류]` 2026-09-04

> ℹ️ **D-054로 보강.** 채널과 프로듀서를 다대다로 바꿨다.

발상: 노래는 결국 유튜브 채널에서 나온다. 채널에 새 영상이 올라온 것을 감지하고,
메타데이터를 AI에 돌려 "이게 노래인가"를 판별하면 곡을 자동으로 추가할 수 있다.

**D-002 덕분에 쿼터 0으로 실현 가능하다:**

```
channel(등록된 프로듀서 채널)
  └ RSS 폴링 (youtube.com/feeds/videos.xml?channel_id=…)
      └ 새 videoId 감지
          └ oEmbed로 제목·채널명·썸네일 확보
              └ AI 판별: 이게 노래인가? (아니면 잡담/티저/쇼츠/라이브 아카이브)
                  └ AI 초안: title_ko / title_en / 원제 / 프로듀서 추정
                      └ 사람 검수 ────> 출제 가능
```

- **자동화는 여기까지다.** 검수를 거치지 않은 곡은 절대 출제되지 않는다.
- RSS는 **최근 15개만** 준다 → 채널 감시는 "앞으로 올라올 것"만 커버한다. 과거 곡 백필은 별도 (O-3).
- WebSub 푸시는 공개 URL이 필요하므로 Phase 2 이후. MVP는 폴링.

### D-010 · 영상에 `playable` 안전장치와 `kind` 분류를 둘 다 둔다 `[확정]` 2026-09-04

- `video.playable` (boolean, 기본 true) — **출제 필터는 이것 하나만 본다.**
  8분 라이브 메들리, 저화질, 무음 구간 긴 영상을 검수 중에 발견하면 이걸 끈다.
- `video.kind` (ORIGINAL / MV / SELF_COVER / COVER / LIVE / OTHER) — **지금은 출제에 쓰지 않는다.**
  메타데이터로만 채워두고, 나중에 "오리지널만" 같은 모드를 만들 때 이미 데이터가 있게 한다.
- **지금 `kind`로 출제를 거르는 코드를 쓰지 않는다.** 데이터만 쌓는다.

### D-011 · 새 영상의 곡 동일성 판별은 "AI 제안 + 사람 결정" `[확정]` 2026-09-04

- AI는 제목·별칭을 비교해 **후보만 제시**한다: `similarSongIds: [42, 88]` + 근거.
- 사람이 검수 화면에서 셋 중 하나를 고른다:
  1. 새 곡으로 등록
  2. 기존 곡 #42의 영상으로 병합
  3. 노래가 아님 → 폐기
- **AI가 자동으로 병합하지 않는다.** 보카로는 제목이 비슷한 별개 곡이 흔해서, 오판 시 서로 다른
  곡이 하나로 합쳐지고 정답 판정이 깨진다. 되돌리기도 어렵다.

### D-012 · 초기 곡 데이터는 미리 수동으로 만든다. RSS는 갱신 전용 `[개정됨 → D-039]` 2026-09-04

> ⚠️ 정신은 유지. **메타데이터 입력 노동만 자동화된다** (D-039).

- Phase 0에서 유명곡 300곡을 사람이 준비한다. (oEmbed로 제목·썸네일은 자동 채움)
- 채널 감시(D-008)는 **"앞으로 새로 올라오는 곡"만** 담당한다. 과거 백필 용도가 아니다.
- 즉 파이프라인은 초기 데이터 확보 수단이 아니라 **운영 중 유지보수 수단**이다.

### D-013 · 프로듀서는 곡당 여러 명 (다대다) `[확정]` 2026-09-04

> ℹ️ **부분 개정 → D-053.** 다대다와 원어 표기 규칙은 그대로다. 연결 테이블이 `song_producer`에서 역할을 가진 `song_credit`으로 바뀌었다.

- `song ↔ producer` 다대다. 합작곡과 작곡/작사 분리를 담는다.
- 이름은 원어 표기 하나만 관리한다 (`wowaka`, `DECO*27`). 별도 결정이 없는 한 번역하지 않는다.
- 범위지정 필터의 "프로듀서" 축은 이 관계를 쓴다.

### D-014 · 보컬(미쿠/린렌 등)은 지금 관리하지 않는다 `[폐기 → D-037]` 2026-09-04

> ⚠️ **뒤집혔다.** 보컬을 관리하기로 했다 (D-037).

- 범위지정 필터는 **프로듀서 / 연도**로 시작한다. 보컬 축은 뺀다.
- 나중에 추가하면 300곡을 다시 훑어야 하는 비용이 있음을 알고 내린 결정.
- 추가 시 `song ↔ vocal` 다대다로 들어간다 (듀엣·합창곡 때문).

### D-015 · YouTube "가장 많이 다시 본 부분"은 쓸 수 없다 `[확정]` 2026-09-04

O-6 검토 중 조사한 결과:

- **공식 API 없음.** Data API v3에 most-replayed / heatmap 엔드포인트가 존재하지 않는다.
- 존재하는 모든 수단이 스크래핑이다:
  - `yt-dlp`의 `heatmap` 필드 — InnerTube 내부 응답과 페이지의 `svg.ytp-heat-map-svg` 파싱 기반.
    자주 `N/A`를 반환한다 (yt-dlp issue #8189).
  - Apify 등 상용 스크래퍼 — 전부 같은 방식.
- **결정적 문제: 히트맵은 조회수가 쌓인 영상에만 생긴다.**
  채널 감시(D-008)로 유입되는 건 신곡이므로, 자동화가 가장 필요한 대상에 데이터가 없다.

**→ 히트맵을 프로덕션 경로에 넣지 않는다.**

### D-016 · 무음 자동 감지는 이 아키텍처에서 불가능하다 `[확정]` 2026-09-04

- 서버는 오디오 파일을 보유하지 않는다 (D-001).
- IFrame Player의 오디오는 cross-origin이라 Web Audio API로 파형을 읽을 수 없다.
- 자동 무음 판정을 하려면 오디오를 내려받아야 하고, 그건 D-001을 세운 이유와 정면으로 충돌한다.

**→ "소리가 나는 지점"은 사람이 정하거나, 규칙으로 정하거나 둘 중 하나다.**

### D-017 · 출제 단위는 사람이 찍은 "구간(Segment)"이다 `[확정]` 2026-09-04

- 검수자가 한 영상에 **여러 개의 구간**을 직접 찍는다.
- 구간 길이는 **5~15초, 최대 20초**.
- **구간이 찍히지 않은 곡은 출제되지 않는다.** 곡이 DB에 있어도 나오지 않는다.
  "출제 가능"의 조건은 곡 등록이 아니라 **구간 존재**다.
- D-016(무음 자동 감지 불가)에 대한 답이다. 자동으로 못 하니 사람이 찍는다.
  대신 여러 개를 찍어서 반복 플레이 시 같은 소리가 나오는 문제(O-9)도 함께 해결한다.
- **용어: `Segment`(구간).** "클립"이라 부르지 않는다.

### D-018 · "점점 길게 들려주기"는 인트로 퀴즈 전용이다 `[확정]` 2026-09-04

**첫 구상에서 바뀐 부분이다. 이전의 힌트 5단계(1/2/4/8/16초) 점수표는 폐기한다.**

- 일반 오디오 퀴즈는 **구간을 통째로 한 번 들려주고** 맞히는 방식이다. 점진 공개가 아니다.
- 시간을 늘려가며 들려주는 방식은 **`INTRO_GUESS` 한 유형에만** 적용한다.
  - 항상 0초에서 시작한다. 구간 지정이 필요 없다.
  - **0.5초부터** 시작해 점점 길게.
  - 단계 상세는 미정 (O-15).
- 즉 두 유형은 필요한 데이터도 진행 방식도 다르다. D-005의 `payload`/`progress` 설계가 이를 감당한다.

### D-020 · 출제 선정 순서는 노래 → 영상 → 구간 `[확정]` 2026-09-04

> ℹ️ **D-055로 보강.** 출제 후보 영상을 `kind = ORIGINAL`로 제한한다.

```
Song 선택  (게임 내 중복 방지는 여기서)
  └ Video 선택   (그 곡의 영상 중에서)
      └ Segment 선택  (그 영상의 구간 중에서)
```

- 구간이 하나도 없는 영상은 후보에서 제외한다.
- 구간이 하나도 없는 곡은 후보에서 제외한다 (D-017).

### D-021 · 구간에는 태그가 붙는다 `[확정]` 2026-09-04

- `Segment`에 태그를 부여하고, 출제 시 **특정 태그만** 내거나 **골고루** 내는 방식을 모두 지원한다.
- 태그 체계 자체는 미정 (O-14).

### D-022 · 자동 파이프라인은 "찾기"만 담당한다 `[확정]` 2026-09-04

- 채널 감시(D-008)의 역할은 **새 곡을 놓치지 않고 초안까지 만들어 두는 것**까지다.
- 구간 찍기(D-017)는 언제나 사람이 한다. 자동 기본 구간을 부여하지 않는다.
- **따라서 곡 수가 늘어도 즉시 게임 콘텐츠가 늘지는 않는다.** 검수 대기열이 쌓이는 것은 정상이며,
  이것을 카탈로그 품질을 보장하는 대가로 받아들인다.

### D-023 · 채점 방식은 퀴즈 유형이 소유한다 `[확정]` 2026-09-04

단일 점수 공식은 없다. 유형마다 다르다.

| 방식            | 설명                                              |
| --------------- | ------------------------------------------------- |
| `SINGLE_SHOT`   | 1회 제출. 맞으면 만점, 틀리면 0                   |
| `TIME_BASED`    | 걸린 시간으로 차등. 서버 시계 기준                |
| `ATTEMPT_BASED` | 시도 횟수로 감점                                  |
| `HINT_BASED`    | 남은 힌트 수로 감점 (힌트를 쓸수록 점수가 깎인다) |

- **다만 D-005의 "라운드 점수는 반드시 0..100" 정규화는 모든 유형에 유효하다.**
  이 계약이 있어서 서로 다른 채점 방식의 유형을 한 게임에 섞어도 총점이 성립한다.
- `QuizType.judge()`가 채점을 소유하므로 별도 배선이 필요 없다.
- `HINT_BASED`가 들어오면서 **힌트 시스템**이 필요해졌다. 힌트가 무엇인지는 미정 (O-20).

### D-024 · 구간 태그는 곡 구조 태그 `[확정]` 2026-09-04

`INTRO / VERSE / PRE_CHORUS / CHORUS / INTERLUDE / OUTRO`

- 검수자가 구간마다 하나를 고른다.
- "후렴만 내기", "골고루 내기" 같은 출제 방식이 여기서 나온다 (D-021).
- 난이도 태그는 두지 않는다. 필요해지면 그때 추가한다.

### D-025 · 장면 이미지는 서버가 저장하지 않는다 — 플레이어를 seek 후 정지 `[개정됨 → D-038]` 2026-09-04

> ⚠️ seek 방식과 불가능 경로 분석은 유효. **"저장하지 않는다"는 단정만 D-038로 완화되었다.**

**조사 결과 (YouTube IFrame Player API 공식 문서):**

- `seekTo(seconds, allowSeekAhead)`는 소수점 초를 받는다.
- 문서 원문: 플레이어는 **"해당 시각 직전의 가장 가까운 키프레임으로 이동한다.
  단 그 구간이 이미 다운로드된 경우는 예외."**
  → 유튜브 키프레임 간격은 통상 2~5초. 그냥 seek하면 그만큼 어긋난다.
  → **우회: 대상 시점 앞에서 미리 버퍼링한 뒤 다시 seek하면 정확해진다.**
  실무 패턴 `seekTo(t-2)` → 음소거 재생으로 버퍼 확보 → `seekTo(t)` → `pauseVideo()`
  → 프레임 단위(1/30초) 보장은 불가. 실질 오차 ±0.1초 수준. 게임에는 충분하다.
- `getDuration()`은 메타데이터 로드 후 사용 가능 (재생 시작 직후). 그 전에는 `0`을 반환한다.

**불가능한 경로 (시도하지 말 것):**

| 방법                        | 왜 안 되나                                                                    |
| --------------------------- | ----------------------------------------------------------------------------- |
| `<canvas>`로 iframe 캡처    | cross-origin이라 `drawImage` 불가, 우회해도 tainted canvas                    |
| 서버에서 ffmpeg 프레임 추출 | 영상 다운로드가 필요 → D-001 위반                                             |
| 임의 시점 썸네일 URL        | 유튜브는 대표 썸네일 + 자동 생성 3장(`1/2/3.jpg`, 대략 25/50/75% 지점)만 제공 |

**따라서:**

- 저장하는 것은 `{videoId, timeSec}` 뿐. 이미지 바이트는 어디에도 저장하지 않는다.
- 모자이크는 플레이어 위 CSS 오버레이 (`filter: blur()` 또는 저해상도 확대)로 구현한다.
- "여러 장 보여주기"는 iframe을 여러 개 띄우면 무겁다. 플레이어 하나를 순차 seek 하거나
  자동 생성 썸네일 3장을 쓴다.

### D-026 · 장면은 "시점 + 용도"로 저장한다 `[방향 확정 · 상세 보류]` 2026-09-04

### D-027 · Segment는 kind로 갈라지고, kind별 속성은 JSON에 둔다 `[폐기 → D-045]` 2026-09-04

> ⚠️ **`kind`로 가르는 것은 유효. JSON 속성은 폐기되었다** (D-045).

O-17의 방향은 "테이블 하나 + `kind` 구분"이 맞다. 다만 **`kind` 값 목록과 kind별 속성은

> 지금 확정하지 않는다.** 지금 못 박으면 나중에 곤란해진다는 판단.

이를 위해 D-005와 같은 패턴을 쓴다:

```
segment
  id
  video_id
  kind         varchar   ← enum 아님. 값이 늘어도 DDL 불필요
  start_sec    numeric
  end_sec      numeric   nullable  (장면처럼 한 점이면 null)
  attributes   json      ← kind마다 다른 속성을 담는다
  created_at
```

- 오디오 구간이면 `attributes = {"structure": "CHORUS"}` (D-024)
- 장면이면 `attributes = {"purpose": "..."}` (D-026)
- **kind 값이 늘어도, 속성이 달라져도 마이그레이션이 없다.**
- 대가: DB 레벨 제약을 못 건다. `kind`별 필수 속성 검증은 애플리케이션 코드가 진다.

### D-028 · 출제 필터에 쓰는 속성만 컬럼, 나머지는 JSON `[폐기 → D-045]` 2026-09-04

> ⚠️ **JSON 자체가 사라져서 이 구분이 무의미해졌다** (D-045).
> D-027의 `attributes` JSON을 유지하되, **출제 시 WHERE 절에 들어가는 속성은 컬럼으로 승격**한다.

```

  id
  video_id
  kind            varchar        ← 값 목록 미정 (O-21)
  start_sec       numeric
  end_sec         numeric  null  ← 장면처럼 한 점이면 null
  structure_tag   varchar  null  ← 컬럼. "후렴만 출제"의 WHERE 절 (D-024)

```

- D-005에서 `primary_song_id`를 밖으로 뺀 것과 같은 논리다.
- 필터가 필요한 속성이 새로 생기면 **그때 하나씩 승격**한다. 미리 다 빼지 않는다.
- `structure_tag` + `kind` 복합 인덱스를 건다.

### D-034 · YouTube Data API를 쓴다 — 단 `search.list`는 쓰지 않는다 `[확정]` 2026-09-05

**D-002를 뒤집는다.** 무료 쿼터가 충분하다고 판단.

**쿼터 사실관계 (정정):**
하루 한도는 "요청 10,000회"가 아니라 **10,000 units**다. 메서드마다 비용이 다르다.

| 메서드               | 비용          | 한 번에 | 하루 처리량                  |
| -------------------- | ------------- | ------- | ---------------------------- |
| `videos.list`        | **1 unit**    | id 50개 | 50만 개 영상 — 사실상 무제한 |
| `playlistItems.list` | **1 unit**    | 50개    | 50만 개                      |
| `channels.list`      | **1 unit**    | id 50개 | 50만 개                      |
| `search.list`        | **100 units** | —       | **하루 100번** ← 유일한 함정 |

**규칙: `search.list`를 코드 어디에도 쓰지 않는다.** 나머지는 자유롭게 쓴다.
곡을 "검색"해야 할 일이 생기면 그건 설계가 잘못된 것이다 — 우리는 videoId를 이미 알고 있어야 한다.

**이 결정이 되살리는 것들:**

| 항목               | 이전 상태                              | 지금                                               |
| ------------------ | -------------------------------------- | -------------------------------------------------- |
| 조회수             | 확보 불가 (D-009 보류 원인)            | `videos.list` `statistics.viewCount`로 확보        |
| 영상 길이          | 클라이언트 `getDuration()` 보고에 의존 | `contentDetails.duration` (ISO 8601)로 서버가 확보 |
| 영상 설명문        | oEmbed가 안 줌                         | `snippet.description` — 챕터 타임스탬프 파싱 가능  |
| **채널 전체 영상** | **RSS 최근 15개만** (D-012의 제약)     | **uploads 재생목록 전량 페이징** ← 가장 큰 변화    |

**채널 전량 수집 방법 (쿼터 거의 안 듦):**

```
channels.list(id, part=contentDetails)          1 unit
  → contentDetails.relatedPlaylists.uploads     채널의 "전체 업로드" 재생목록 ID
playlistItems.list(playlistId, maxResults=50)   1 unit × 페이지 수
  → 영상 500개짜리 채널이면 총 11 units
```

→ 하루 10,000 units면 **채널 수백 개를 통째로 긁을 수 있다.** D-012 재검토 필요 (O-24).

**여전히 불가능한 것 (변하지 않음):**

- **most-replayed / 히트맵** — Data API에 엔드포인트 자체가 없다 (D-015 유효)
- **무음 구간 자동 감지** — 오디오 파형을 주지 않는다 (D-016 유효)

**RSS와 oEmbed는 계속 쓴다.** 쿼터를 소비하지 않으므로 잦은 폴링에 적합하다.
최적 조합: **신규 감지는 RSS(공짜, 자주) → 상세 메타데이터는 Data API(정확, 배치)**.

### D-049 · 개발·운영은 MySQL, 테스트는 H2 `[확정]` 2026-09-07

**`02-ARCHITECTURE.md` §1의 "개발 H2 → 운영 PostgreSQL"과 §13의 "관리형 PostgreSQL"을 뒤집는다.**

MySQL이 더 익숙하고, 지금 따로 공부하고 있는 대상이기도 하다. 1인 개발에서는 DB의 기술적 차이보다 숙련도가 개발 속도를 더 좌우한다. PostgreSQL이 이 프로젝트에 필요한 무언가를 더 주는 것도 아니다.

| 프로파일 | DB                       | `ddl-auto`    |
| -------- | ------------------------ | ------------- |
| `dev`    | MySQL `localhost:3307`   | `update`      |
| `test`   | H2 인메모리 `MODE=MySQL` | `create-drop` |

계정은 `config/local.yaml`로 빼고 git이 추적하지 않는다.

따라오는 것:

- dev가 인메모리가 아니게 되면서 `ddl-auto`가 갈렸다. MySQL에 `create-drop`을 걸면 재기동마다 실제 테이블이 사라진다. **P1-5에서 손으로 찍을 구간 데이터가 여기 들어가므로** dev는 `update`다.

- CI 러너에는 MySQL이 없다. 테스트가 `test` 프로파일의 H2로 붙어야 아무 준비 없이 돌아간다.

### D-051 · 곡의 언어는 다대다. 가사 언어를 여기에 통합한다 `[확정]` 2026-09-08

**D-044를 개정한다.**

일본어와 한국어가 절반씩인 곡이 최근 늘었다. 단순히 영어가 섞이는 수준이 아니라 두 언어로 불리는 곡이다. 언어를 하나만 고르면 그 순간 거짓이 된다.

- `song_language(song_id, language_id)` 다대다로 바꾼다.
- `song.lyrics_language_id`를 여기에 통합한다. 곡 자체의 언어가 가사의 언어보다 포괄적이고 중요하다.
- 복합 언어 곡은 해당 언어 필터 **모두에** 걸린다. 주 언어를 표시하지 않는다.
  일본어 필터에 절반이 한국어인 곡이 나오는 것을 감수한다. 필요해지면 그때 주 언어 표시를 더한다.
- `song.original_language_id`는 남는다. 뜻은 "원제가 어느 언어인가"이고, 원제 병기(D-007)가 쓴다.

### D-052 · 정답 후보는 패턴 원문에서 전개한다 `[확정]` 2026-09-08

> ⚠️ **부분 개정 → D-056.** 패턴에서 전개한다는 결정은 유효하다. 다만 패턴이 `song_name`의 컬럼이 아니라 별도 테이블 `song_answer_pattern`으로 갈렸고, 언어 구분이 없어졌다.

**D-040을 보강한다.** 곡 이름을 한 테이블로 모은다는 결정은 그대로다.

히토마니아는 (히토 · 인간 · 사람) × (마니아 · 매니아)의 조합으로 불린다. 이걸 사람이 여섯 줄로 적는 것은 지치는 일이고, 빠뜨리면 그 표기로 검색한 사람이 곡을 못 찾는다.

- `song_name.answer_pattern` — 사람이 쓰고 고치는 원문. **진실.**
- `song_name_answer` — 전개 결과. **파생.** 원문이 바뀌면 그 행들을 통째로 다시 만든다.
- 문법은 괄호와 파이프만. `(히토|인간|사람)(마니아|매니아)`
  문자 자체가 필요하면 `\(` `\|` `\)` `\\`로 이스케이프한다. NULL이면 `name` 하나만 전개된다.
- 전개가 20개를 넘을 것으로 보이면 관리자 입력 창에서 경고한다. 저장을 막지는 않는다.
- 정규화(NFKC → 소문자 → 기호 제거 → 가타카나→히라가나)는 `song_name_answer`에 적용된다.
  `song_name.normalized`와 `song.search_keywords`는 없앤다.
- 화면에 보여줄 이름은 `song_name`이다. 전개 결과를 목록에 섞지 않는다.

**정답 판정은 바뀌지 않는다.** 정답창에 입력하면 이 테이블로 후보를 띄우고 사용자가 고른다. 서버가 받는 것은 여전히 `songId`다 (02-ARCHITECTURE §7). 자유 텍스트를 받을 것인가는 O-33으로 남긴다.

### D-053 · 크레딧에 역할 축을 둔다 `[확정]` 2026-09-08

**D-013을 개정한다.** 곡당 여러 명이라는 것과 원어 표기 하나라는 규칙은 그대로다.

지금은 프로듀서를 곡에만 달 수 있어서 **리믹서를 적을 자리가 없다.** 작곡·작사·조교가 갈리는 곡, 일러스트와 영상 담당도 마찬가지다.

```
song_credit  (song_id, producer_id, role)
video_credit (video_id, producer_id, role)
```

- 테이블을 둘로 나눈다. 하나에 `target_type`을 두면 FK를 걸 수 없다.

### D-054 · 채널과 프로듀서는 다대다 `[확정]` 2026-09-08

**D-008을 보강한다.**

`channel.producer_id` 하나로는 합작 채널을 담지 못한다. 드물지만 존재하고, 한 프로듀서가 채널을 여럿 쓰기도 한다.

- `channel_producer(channel_id, producer_id)`로 뺀다.
- **조인 엔티티로 만든다.** `@ManyToMany`는 컬렉션에서 하나를 빼면 조인 행을 전부 지우고 다시 넣는 일이 흔하고, 나중에 속성을 붙일 자리가 없다.
- 양쪽에서 `@OneToMany`로 탐색한다. 대표 프로듀서 표시는 두지 않는다.
- 지금 바꾸는 이유는 행이 하나도 없어서 공짜이기 때문이다. 데이터가 쌓인 뒤에는 이관이 붙는다.

### D-055 · 출제 대상 영상을 `kind = ORIGINAL`로 제한한다 `[확정]` 2026-09-08

**D-020을 보강한다.**

정답은 원곡 기준이다(D-011). 그런데 리믹스 영상을 문제로 내면 "원곡 제목을 답해야 하는" 어색함이 생긴다. 리메이크가 원곡과 많이 다를수록 심해진다.

- 출제 후보 영상을 `kind = ORIGINAL`로 제한해 어색함을 **만들지 않는 쪽**을 택한다.
- 리믹스 영상은 저장하되 출제하지 않는다.
- **정답 범위는 퀴즈 유형이 소유한다.** 채점 방식을 유형이 갖는 것(D-023)과 같은 원리다.
  리믹스를 일부러 내는 유형이 생기면 그 유형이 스스로 조건을 정한다. 전역 규칙을 고치지 않는다.
- 리믹스가 독립된 제목으로 인지도를 얻는 사례가 늘면 `song` 승격과 `derived_from`을 다시 본다.
  30곡을 채우고 게임을 돌려 본 뒤에 판단한다. 지금은 판단 재료가 없다.

### D-056 · 보여주기용 이름과 정답용 패턴을 나눈다 `[확정]` 2026-09-09

**D-052를 부분 개정한다.** 패턴에서 후보를 전개한다는 것은 그대로다.

`song_name`이 두 가지 일을 겸하고 있었다.

| 하는 일   | 언어가 필요한가                                 |
| --------- | ----------------------------------------------- |
| 보여주기  | **필요하다.** 언어별 대표 이름을 골라야 한다    |
| 정답 처리 | **필요 없다.** 어느 표기든 같은 songId로 모인다 |

정답 판정에 언어가 왜 필요한지 물으면 답이 없었다. `song_name`에 얹었기 때문에 딸려온 것이지 필요해서가 아니었다.

그래서 갈랐다.

```
song_name              보여주기 전용. language_id · is_primary 유지
song_answer_pattern    정답 패턴 원문. 곡당 한 행. 언어 없음
song_answer            전개 + 정규화 결과. UNIQUE (song_id, normalized)
```

**이 분리가 없애는 문제 셋:**

- **언어가 달라 텍스트가 같은 중복.** `ko`와 `en`에 똑같이 "Mesmerizer"가 있으면 후보가 두 번 떴다.
  정답 쪽에 언어가 없으니 애초에 생기지 않는다.
- **조회 DISTINCT.** `UNIQUE (song_id, normalized)`가 곡 단위로 막으므로 합칠 것이 없다.
- **정답 원문이 곡 조회에 딸려 오는 경로.** 테이블이 갈려 실수로 응답에 섞일 길이 사라진다 (CLAUDE.md §1.1).

**따라오는 것:**

- 패턴은 **곡당 한 행**이다 (`song_id` UNIQUE). 여러 표기는 한 텍스트 안에 줄로 나열한다.
  줄은 `\R`로 자르고 각 줄을 `strip()`하며 빈 줄은 버린다.
- 한 줄이라도 문법이 틀리면 **전체가 실패한다.** 조용히 한 줄만 빠지면 검색되지 않는 곡이 생기고 아무도 모른다.
- 중복 제거는 전개기가 하지 않는다. 정규화 후에 `SongCatalogService`가 한다.
- 전개 개수는 **전개하기 전에** 곱으로 센다. 20개 경고와 폭발 방어에 쓴다.
- 전개 순서는 줄 순서 → 각 줄 안의 곱 순서다.
- 패턴 출처(`song_answer_pattern_id`)를 `song_answer`에 남기지 않는다.
  곡 단위로 중복을 지우면 어차피 "먼저 온 것"만 남아 부정확해진다.

**잃는 것:** 언어별 후보 필터가 불가능해진다. 다만 범위지정 필터의 언어 축은
`song_language`(곡의 언어)를 쓰지 정답 후보의 언어를 쓰지 않는다. 필요해지면
`song_answer_pattern`에 언어를 더하면 된다.

## 이 로그를 쓰는 법

1. 결정을 코드보다 **먼저** 적는다.
2. 확정된 것만 `[확정]`. 안 정한 것은 `[보류]`로 남기고 **무엇을 알아야 정할 수 있는지** 적는다.
3. 번호를 재사용하지 않는다.
4. 뒤집힌 결정을 **지우지 않는다.** `[개정됨 → D-xxx]` 또는 `[폐기 → D-xxx]`를 달고,
   왜 뒤집혔는지 한 줄 적는다. **그 기록이 이 파일의 값어치다.**
5. 미해결은 `O-번호`로 표에 남긴다. 해결되면 `~~O-n~~ → D-xxx`로 지운다.
