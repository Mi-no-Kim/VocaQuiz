# TIL 작성 규칙

## 왜 쓰는가

이 기록의 독자는 세 명이다:

1. **3개월 뒤의 나** — "왜 이렇게 짰지?"에 답해야 한다
2. **면접관** — 기술 선택의 근거를 볼 사람
3. **지금의 나** — 쓰면서 이해가 정리된다

세 독자 모두 **"오늘 GameService를 만들었다"에는 관심이 없다.**
전부 **"왜 그렇게 결정했는가"**를 보러 온다.

---

## 언제 쓰는가

**"1일 1TIL"이 아니다. 1커밋 1TIL도 아니다.**

> **막혔다가 풀렸을 때 쓴다.**

구체적으로:

- 30분 이상 헤맨 문제를 해결했을 때
- 두 가지 방법 중 하나를 고르느라 고민했을 때
- 예상과 다르게 동작해서 이유를 파고들었을 때
- Phase 하나가 끝났을 때 (회고)

**쓰지 않는 날이 있어도 된다.** 막힘 없이 잘 굴러간 날에 억지로 쓴 글은 아무도 안 읽는다.

---

## 형식

- 위치: `docs/til/`
- 파일명: `YYYY-MM-DD-짧은-슬러그.md` (예: `2026-09-08-round-state-transition-on-get.md`)
- 하루에 여러 개면 슬러그로 구분한다 (번호를 붙이지 않는다)
- 템플릿: `_TEMPLATE.md`

## 좋은 TIL / 나쁜 TIL

|         | 나쁨                           | 좋음                                                                         |
| ------- | ------------------------------ | ---------------------------------------------------------------------------- |
| 제목    | `2026-09-08 개발일지`          | `GET 요청이 게임 상태를 바꾸고 있었다`                                       |
| 첫 문단 | "오늘은 라운드 API를 만들었다" | "새로고침 5번이면 답을 다 들을 수 있는 버그를 찾았다"                        |
| 내용    | 코드 전체 붙여넣기             | 문제 코드 5줄 + 왜 틀렸는지                                                  |
| 끝맺음  | "다음엔 프론트를 할 예정"      | "GET을 멱등하게 만드는 게 REST 규약이 아니라 실제 보안 요구였다는 걸 배웠다" |

**코드는 최소한만.** 이 문제를 이해하는 데 꼭 필요한 몇 줄만 넣는다.
전체 코드는 GitHub에 있다. TIL은 코드가 아니라 **판단**을 남기는 곳이다.

쓰는 데 20분 넘게 걸리면 너무 많이 담으려는 것이다. 잘라라.

## 이 프로젝트에서 나올 좋은 TIL 소재 (미리 찍어 둔 것)

작업하다 이 지점에 도달하면, 그때가 쓸 때다.

**설계 / 의사결정**

- **결정 로그를 만들고 D-번호로 관리한 이유** — 47개를 정하는 동안 5개가 뒤집혔다.
  뒤집힌 기록을 지우지 않는 것이 왜 값어치가 있는가
- **"구현체 하나뿐인 인터페이스는 과설계"라는 내 규칙에 예외를 둔 날** (D-005, 02-ARCH §4.4)
  — *예정*인가 *상상*인가로 판단 기준을 세운 과정
- **JSON 컬럼을 넣었다가 빼기까지** (D-027 → D-045) — "유한하고 예측 가능하면 컬럼"
- **YouTube Data API를 안 쓰기로 했다가 쓰기로 바꾼 날** (D-002 → D-034)
  — 제약 하나가 풀리자 되살아난 결정 네 개

**YouTube 연동**

- `search.list`가 다른 메서드보다 100배 비싼 것과, 그래서 설계가 바뀐 이야기 (D-043)
- "가장 많이 다시 본 부분"을 쓰려다 포기한 과정 — 공식 API가 없고, 신곡엔 데이터가 없다 (D-015)
- 무음 감지를 자동화할 수 없다는 걸 알게 된 순간, 그것이 D-017(사람이 구간을 찍는다)을 낳은 과정
- 채널 RSS(쿼터 0)와 Data API를 조합한 이유

**데이터 모델**

- 곡 1 : N 영상 — 셀프커버가 정답 판정을 어떻게 흔들었나 (D-006)
- `song_alias`를 없애고 `song_name`으로 합친 날 — `is_primary` 하나로 표시와 검색이 갈린다 (D-040)
- 제목 언어와 가사 언어를 **다른 컬럼**으로 둔 이유 (D-044)
- 왜 자유 텍스트 입력 대신 자동완성을 골랐나 — 그리고 그걸 **전역 규칙이 아니라 유형별 선택**으로
  격리한 이유 (`LYRIC_BLANK`가 언젠가 올 것을 알기에)
- `ORDER BY RANDOM()`을 안 쓴 이유 — 중복 배제와 데일리 재현성

**Phase 1 (관리자 → 구간 → 게임)**

- 관리자 페이지가 "편의 기능"에서 "게임의 전제 조건"이 된 날 (D-030)
- 프론트를 모르는 채로 가장 어려운 화면(구간 찍기)부터 시작한 기록
- GET이 상태를 바꾸면 생기는 일 — 멱등성이 규약이 아니라 보안인 순간
- DTO를 안 쓰고 엔티티를 반환했다가 정답이 새어 나간 사건
- 익명 유저와 로그인 유저를 `owner_key` 하나로 다루기

**Phase 3 · 5 — 설계 검증 관문**

- **두 번째 퀴즈 유형을 추가하며 `git diff --stat`을 확인한 날** — 계약이 맞았는지 틀렸는지
  숫자로 드러나는 순간. 틀렸다면 그것도 똑같이 좋은 글이 된다
- 두 유형의 채점이 똑같아 보였지만 공통 클래스로 뽑지 않은 이유
- 곡 2개·1회 시도인 `VIEW_BATTLE`이 기존 계약에 그대로 들어갔는가

**Phase 4**

- 인메모리 방 상태의 대가 — 무엇을 포기했고 왜 괜찮은가
- 타임아웃 스케줄러와 마지막 정답이 동시에 라운드를 끝내려던 경합
- 서버 시각으로만 점수를 계산하면서 클라이언트 카운트다운을 맞춘 방법

**전체**

- AI 파이프라인에 "판단"이 아니라 "제안"만 시킨 이유 (D-011)
- 1인 개발에서 테스트를 4종류로 줄인 기준

## 마지막 규칙

**TIL을 쓰려고 개발을 멈추지 않는다.**
막힌 걸 먼저 풀고, 풀린 직후에 기억이 선명할 때 20분 안에 쓴다.
